# Deployment & operations

Two artifacts: a **static web app** (`apps/web/dist`) and one **Node game server** (`apps/server/dist`).
Nothing here is deployed for you: the repository contains the build, container and blueprint files; creating
the hosting account and applying them is a manual step.

## What was verified (and what was not)

| Item                                                                                   | Status                                                                       |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |

## Environment variables (server)

See `.env.example`. Required in production: `CLIENT_ORIGINS` (exact origin(s) of the web app) and, behind a
proxy, `TRUST_PROXY=true`. Strongly recommended: `METRICS_TOKEN`.

## First deploy on Render (steps for you)

1. Push the repository to GitHub and connect it in Render: **New > Blueprint**, pick this repo (`render.yaml`).
2. Apply. Two services are created: `zhb-server` (Docker web service) and `zhb-web` (static site).
3. Set the two `sync: false` values:
   - `zhb-server` > `CLIENT_ORIGINS` = the URL of `zhb-web` (e.g. `https://zhb-web.onrender.com`)
   - `zhb-web` > `VITE_SERVER_URL` = the URL of `zhb-server`, then **redeploy `zhb-web`** (the value is baked in at build time)
4. Open the web URL, create a private room, join from a second browser, play a round.
5. Optional hardening: replace `connect-src ... https: wss:` in the CSP with the exact server origin.

`METRICS_TOKEN` is generated by Render; read it from the service environment to scrape `/metrics`.

## Scaling limits (read before growing)

- **Run one server instance.** Rooms live in process memory and the default Colyseus presence/driver are
  local. Two instances behind a load balancer would split rooms and break join-by-code. Scaling out needs
  Redis presence + a shared matchmaking driver (not implemented).
- Measured capacity of one process (see `PERFORMANCE.md`): about **40-60 simultaneous 2v2 rooms (160-240
  players)** on a modern core before event-loop lag approaches one frame. 5v5 rooms cost roughly 3-5x a 2v2
  room. `MAX_ROOMS` protects the process; players get "server is busy" when it is hit.
- Deploys and restarts end running matches (rooms are not persisted). Deploy during low traffic.

## Operations

- Liveness `GET /health`, readiness `GET /ready` (used by the container health check and Render).
- `GET /metrics` (JSON) or `GET /metrics?format=prom` (Prometheus text): rooms, clients, sim tick p50/p95/p99/max,
  event-loop lag, memory, counters (rooms created, matches, inputs, client errors, rejected upgrades).
- **Suggested alerts:** `simStepMs.p99 > 8` (half a frame), `eventLoopLagMs.p99 > 12`, `memoryMB.rss` growing
  without bound across hours, `upgradesRejected` spiking (attack or misconfigured `CLIENT_ORIGINS`).
- Logs are JSON lines for the events that matter: `client_error` (browser exceptions, via `/client-errors`),
  `unhandled_rejection`, `uncaught_exception`. Alert on any `uncaught_exception`.
- Graceful shutdown: SIGTERM lets Colyseus close rooms; the process logs the signal.
- Rollback: redeploy the previous image/commit; there is no database or migration to unwind.

## Load testing

```bash
npm run build -w @zhb/server
# raise the per-IP connection budget on the server under test, since all bots share one address:
UPGRADE_BURST=5000 MAX_ROOMS=500 node apps/server/dist/index.js &
npm run loadtest -- --url ws://localhost:2567 --rooms 40 --players 4 --seconds 30
```

Run the generator on a different machine for numbers closer to production; on the same machine it competes
with the server for CPU and understates capacity.
